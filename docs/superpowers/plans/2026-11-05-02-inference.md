# 02 · Inference Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One `weave_inference` package that every stage uses to call a model: a catalog of models, providers and deployments loaded from `inference.yaml`; readiness probing; one client per wire format with local limit checks, rate limits and retries; a ledger row per call; a ledger-based cost estimator; and a deterministic stub provider for CI.

**Architecture:** `weave_inference` depends on `weave_core` only. `Catalog` (built from `inference.yaml` plus a probe) implements core's `DeploymentCatalog`, so `RunService` refuses runs with unready or wrong-capability deployments without changes to `validate()`. Stage adapters get an `Inference` object from `Inference.for_context(ctx)`; it resolves the run's deployment for a capability, picks the wire client by the provider's `kind`, enforces the deployment's limits and rate limits, and writes one ledger row per call in its own transaction (so spend is recorded even when the job later fails). Ledger and readiness tables go into core's single Alembic chain as `0002_inference`.

**Tech Stack:** Python 3.12, httpx (sync, `MockTransport` in tests), Pydantic 2, PyYAML, SQLAlchemy 2.1, Alembic, Typer, pytest.

**Spec:** `docs/superpowers/specs/2026-11-05-mvp/02-inference.md` (and `00-overview.md`, `01-core.md`; core plan `docs/superpowers/plans/2026-11-05-01-core.md`).

## Global Constraints

- Python `>=3.12,<3.13`; package `weave-inference` in `packages/inference`, depends on `weave-core` only. Stage packages may depend on it.
- Models, providers, deployments are separate types. Runs and ledger rows always point at a **deployment** ID, never a model ID.
- Capabilities are core's `Capability` enum: `system_one`, `llm`, `embeddings`, `extraction`.
- Provider config holds the **name** of an env var for credentials, never the secret. `.env.example` documents each one.
- OpenRouter is the default provider for `system_one`, `llm`, `embeddings` when a run names no deployment.
- llama.cpp: a model is `system_one` only if `architecture.output_modalities` contains `decisions`. A plain LM is never `system_one`.
- Readiness reasons, exact strings: `unreachable`, `model missing`, `capability not advertised`, `credential missing: <VAR>`. Rendered as `not ready: <reason>`.
- Over-limit requests (context size, Choice option count, request size) are refused locally, never sent.
- `429` honours `retry-after` (seconds or HTTP date). Transient errors (connect/read timeouts, 5xx) retry with exponential backoff; 3 attempts total, matching core. Core's job retry policy applies on top.
- Cost from provider-reported usage/price when present; otherwise deployment price × tokens with `estimated = true`. Local deployments: cost `0`, latency recorded.
- No test touches the network. `weave inference smoke` is never run in CI.
- Wire formats for Liquid, Baseten and any provider not named in the spec are not implemented here; adding one means checking its docs first.
- Tests use the real Postgres from the core plan (`podman run ... pgvector/pgvector:pg17`).

**Scope decision (this plan):** Implemented provider kinds: `llamacpp`, `typesafe`, `openrouter`, `cloudflare`, `openai` (generic OpenAI-compatible, e.g. vLLM), `stub`. Request/response shapes for each vendor are taken from that vendor's current docs at implementation time and pinned as JSON fixtures under `packages/inference/tests/fixtures/<kind>/`; tests assert our typed mapping against those fixtures.

## Review Focus

1. A provider returns `200` but no `usage` block: the ledger row still appears, cost computed from deployment prices, `estimated = true`, never `NULL` cost. (Task 4)
2. A call fails after all retries (or is refused locally): exactly one ledger row with `status` `error`/`refused`, the typed error reaches the adapter, and core fails the job normally. (Task 4)
3. A cached stage output is reused by a second run: no model call and no new ledger row. (Task 7)
4. `retry-after` given as an HTTP date, or absurdly large (> 300 s): parsed, capped at 300 s, and not treated as a crash. (Task 5)
5. Probing with a provider that hangs: the probe times out (5 s per provider), the deployment is `not ready: unreachable`, and other providers are still probed. (Task 3)

### Task 8: Cost estimator, readiness snapshot on start, CLI wiring

**Files:**
- Create: `src/weave_inference/{estimate,cli}.py`
- Modify: `packages/core/src/weave_core/runs.py` (optional `on_start(session, run_id, cfg)` hook arg on `RunService`), `packages/core/src/weave_core/cli.py` (if `weave_inference` importable: catalog from `WEAVE_INFERENCE_FILE` + probe, `LedgerEstimator`, `on_start=store_readiness`, `Inference.configure` in `worker`, `app.add_typer(inference_app, name='inference')`; else current `StaticCatalog` path), `packages/inference/pyproject.toml`
- Test: `tests/test_estimate.py`, `tests/test_cli.py`

**Interfaces:**
- Produces:
  - `Estimate(amount: Decimal | None, reason: str | None)` in `weave_core.runs`; core `CostEstimator.estimate(cfg) -> Estimate`, `NoEstimate` returns `Estimate(None, "no estimator")`, `RunCreated.estimate: Estimate`.
  - `LedgerEstimator(engine, registry)` implementing that protocol. For each stage with deployments: `avg = sum(cost)/count(distinct job)` over ledger rows matching `(adapter, deployment)` with status `ok`; units = jobs of that stage in the most recent run whose provide `input_hash` equals this config's provide hash, minus those whose recomputed `cache_key` (core `cache_key`) exists in `stage_outputs`.
