# 05 · Enrichers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `weave_enrichers` package with three interchangeable `enrich`-stage adapters (`clairic`, `nuextract3`, `system-one`) that describe each mention by action, participants, location and time, using only text found in its document, plus coverage reporting.

**Architecture:** Each enricher is a core `StageAdapter` for `Stage.enrich` with input unit `mention`. It reads its mention from `upstream[Stage.extract]["mentions"]` (as the significance tagger does), loads the document with `weave_extractors`-style `load_document` (copied, since stage packages never import each other), builds a marked window, calls `weave_inference`, and passes every answer through one shared verifier that locates text by exact match or discards and counts it. Output is `{"enrichment": {...}, "discarded": n}` plus a row in a new `enrichments` table. Enrich emits the same mention unit forward so `embed` (06) gets one job per mention.

**Tech Stack:** Python 3.12, SQLAlchemy 2.1 + Alembic (core chain), Pydantic 2, httpx (stanza client), pytest. No new third-party dependencies.

**Spec:** `docs/superpowers/specs/2026-11-05-mvp/05-enrichers.md` (with `00-overview.md`, `01-core.md`, `02-inference.md`, `04-mention-extractors.md`; prior plan `2026-11-05-04-mention-extractors.md`).

## Global Constraints

- Package `weave-enrichers` in `packages/enrichers`; depends on `weave-core` and `weave-inference` only. Never imports `weave_extractors` or `weave_providers`: copy `Doc`, `load_document`, `iso`, the Stanza `Word`/`Sentence`/`StanzaClient`/`HttpStanzaClient`/`FixtureStanzaClient` types and `mark()` (marker `⟦…⟧`) into `weave_enrichers/_shared.py`, each with a one-line comment naming the original.
- Adapters registered via entry-point group `weave.adapters`: `clairic`, `nuextract3`, `system-one` (stage `enrich`, `input_kind=mention`). Version `"1"` each.
- Enrichment shape (per field `action`, `participants`, `location`, `time`): `text: str | None`, `spans: list[[start, end]]` (document char offsets), `confidence: float | None`; `time` adds `normalized: str | None` (ISO 8601 date, date-time, or `start/end` interval). `participants.text` is the participant texts joined with `"; "`, one span per participant.
- **Invariant for every adapter:** for each non-empty field, every span satisfies `document.text[s:e]` == that span's text, and the field's text is built only from those slices. Text not found exactly in the document is discarded and counted (`output["discarded"][field]`), never fuzzy-matched.
- Adapter input: title, outlet, `published_at`, and a window of `window_sentences` sentences on each side of the mention's sentence, with the trigger wrapped as `⟦trigger⟧`. `window_sentences` is a setting per adapter (default 1) recorded in the frozen run config.
- System One: no model call for `action`; no Choice with more options than the deployment's `limits.max_choice_options` (split the candidates into rounds of that size, winners compete in a final round); joint deployments (`Deployment.joint`, e.g. Clef) get one request per mention; `time.normalized` always `None`.
- Thresholds (`participant_threshold`, `stated_threshold`) are required System One settings in `0..1`, chosen later on English dev and recorded in the run config.
- No test touches the network or needs Stanza installed; models via the stub provider, parses via fixture client. Tests use the real Postgres from the core plan.

## Review Focus

1. A field answer that occurs several times in the document (e.g. "Monday", "police"): pick the occurrence closest to the trigger (smallest distance, ties to the earlier), never the first in the document. (Task 2)
2. A mention whose window holds another mention of the same word: only the marked one is wrapped, by offset not by string replace. (Task 2)
3. A Clairic or NuExtract3 answer with different whitespace or case ("Police" vs "police"): discarded and counted, not normalised to a match. Spec says exact. (Tasks 2, 4, 5)
4. A document with no `published_at` (some MCECR docs): `time.normalized` is `None` and the request omits the date line; no crash. (Tasks 4, 5)
5. A System One mention whose window has zero location or time candidates: no Choice is sent for that field, field empty, no Choice with fewer than 2 options. (Task 6)

### Task 4: Clairic enricher

**Files:** Create `clairic.py`, `tests/test_clairic.py`.

**Interfaces:**
- Consumes: `Inference.for_context(ctx).extract(ExtractionRequest(text, fields))` → `ExtractionResponse.fields: dict[str, list[Span]]`; `Limits.max_fields`.
- Produces: `ClairicEnricher`, `capabilities={extraction}`, settings `{window_sentences: int = 1}`. Fields per mention `m{i}_action`, `m{i}_participants`, `m{i}_location`, `m{i}_time`, each with an instruction from `FIELD_INSTRUCTIONS` (module constant, one sentence per field, all about "the event marked ⟦like this⟧"; Diego reviews wording). Request text = header + window. Each returned `Span` is checked: `window.text` passage must equal `span.text` and map back to the doc (strip markers, add `offset`); otherwise discarded. Confidence = span confidence (max over kept spans).
- Batching: the spec allows several mentions of one document per request. Core runs one job per mention, so batching is done by a per-document cache inside the adapter: `enrich_document(doc, mentions) -> dict[mention_id, Enrichment]` packs `floor(max_fields / 4)` mentions per request using one shared window that spans them, and stores results in a process-local LRU keyed `(doc.id, deployment)`. A job takes its own mention's result. (If the worker restarts, the next job recomputes; results are deterministic through the inference cache.)

- [ ] **Step 1: Tests** — stub returns `police` (exact) and `Police force` (not in doc) for participants → one span, `discarded["participants"] == 1`; `test_batches_by_field_limit` (`max_fields=8`, 3 mentions in one doc → 2 requests in ledger, 3 enrichments); `test_marker_offsets_removed` (span after the `⟦` marker maps to the right doc offset); contract suite.

### Task 6: System One candidate-choice enricher

**Files:** Create `system_one.py`, `tests/fixtures/stanza/*.json`, `tests/test_system_one.py`; compose: give the worker `WEAVE_STANZA_URL` if not already set.

**Interfaces:**
- Consumes: copied `StanzaClient`; `Inference.system_one(SystemOneRequest)`; `Noul`, `Choice`, `Deployment.joint`, `limits.max_choice_options`, `LimitExceeded`.
- Produces:
  - `proposals(window_sentences: list[Sentence], trigger_word_idx) -> Proposals(participants, locations, times, action_span)` built in code: participants = named entities (PER, ORG, NORP…) plus noun phrases (head + `det/amod/compound/flat/nmod` children, contiguous only) attached to the trigger by `nsubj, nsubj:pass, obj, iobj, obl, obl:agent`; locations = entities `LOC/GPE/FAC` and `obl` phrases whose case marker is a locative preposition list per language (module constant); times = entities `DATE/TIME` and `obl:tmod`/`nmod:tmod` phrases; action = trigger plus contiguous `aux:pass, compound:prt, xcomp` heads attached to it (no model). The Stanza service needs `ner` added to its pipelines for languages that have it; where a language lacks NER, only the dependency phrases are used (note it in the report).
  - `SystemOneEnricher`, `capabilities={system_one}`, settings `{participant_threshold: float, stated_threshold: float, window_sentences: int = 1, stanza_url: str | None = None}` (both thresholds required).
  - Questions: `Noul(id="p{i}", prompt=f"Is “{c}” a participant in the marked event?")`; `Noul(id="loc_stated", "Does the text state where the marked event happened?")` + `Choice(id="loc", options=[...])`; same for `time`. State = header + marked window. Field filled only when `stated ≥ stated_threshold`; confidence = Choice probability of the winner. Choice skipped when it would have <2 options (1 candidate: use that candidate, still gated by the Noul).
  - Packing: non-joint deployments get all of a mention's questions in one request, split on `LimitExceeded` by halving; joint deployments always one request per mention. Choices larger than `max_choice_options` run as rounds of that size; round winners go to a final Choice.
